# Superpowers migration

Treat detected names as evidence of references, not proof that a plugin or hook is active. Inspect project-local instructions, existing task/plan catalogs and host-visible skill selectors first. User-level installation/settings require separate permission; do not search home directories or credential files to guess configuration.

1. Ask replacement or coexistence if not already decided. Replacement gives ND ownership of future delivery routing. Coexistence requires explicit ownership of planning, execution, tests and verification; conflicting mandatory triggers are unresolved until reviewed.
2. Inventory active work: requirement/design paths, implementation plans, unfinished tasks, current branch/changes, previous checks and owners. Preserve original paths and history. Existing designs can inform specs; plans can be linked from task checkpoints; old checks remain historical until verified against current state. These are mappings, not exact format conversions.
3. Compare policy semantics: ND uses highest applicable risk, optional delegation and test-first where practical. Do not silently retain a conflicting always-on workflow or weaken existing project security controls. Identify each rule to preserve, supersede or resolve.
4. Preview ND additions and instruction merges. For replacement, list exact old project-local references or triggers proposed for retirement and obtain explicit authorization. Never remove global Superpowers installation as a side effect. If host-managed activation cannot be changed within approved scope, report blocked cutover rather than successful migration.
5. For coexistence, retain distinct selectors and document selected owner per task. Do not run both full delivery workflows for the same task. Keep useful independent skills only under the agreed routing rules.
6. Verify a fresh session selects intended workflow for a small change and treats a one-line auth change as critical. Inspect host context where available; model self-report alone is insufficient. Confirm existing plans and unfinished work remain accessible, then select next task.

Recovery: preserve instruction backups, prior configuration references and work inventory. Revert only reviewed migration changes, not unrelated application work. Do not delete original plans, reset branches, uninstall global plugins, or fabricate passing app checks.
