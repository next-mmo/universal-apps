# Spend tokens where they change the result

Identify the next decision, the evidence needed, and a stopping condition using the existing task. Reuse available context and prior outputs; do not create another plan, recap, or log merely to run this skill.

Discover paths or symbols first, then read the relevant section. Bound output at the source, including status listings and error streams; output truncation can hide the answer. Search tracked and relevant untracked files where needed without traversing unrelated generated or runtime directories. Expand only for a specific unresolved question. A bounded search must not become a claim of exhaustive coverage.

Batch independent reads and checks when the tools are known to work. Verify an unfamiliar wrapper with one small call before sending a batch through it. On failure, identify and change the cause before retrying; follow the repository's executable-resolution rule. Avoid nested shell interpolation; prefer literal arguments or a saved script for complex commands. Do not change global environment settings to hide a local tool issue.

Use the cheapest check that proves the affected behavior, including required regression, API, UI, and release checks. Token savings never justify skipping required verification or calling incomplete work done. Reuse running services and valid build results when applicable. Repeat only after a relevant change, a failure diagnosis, or an unresolved coverage gap.

Use delegation only when authorized and independent work justifies its context cost. Avoid duplicate investigations, unchanged polling, and routine full skill loading. Route once to a specialist only when its procedure changes the next action.

Finish once the requested outcome and necessary checks are satisfied, or state the specific blocker. Report measured tokens or time only when exposed by tools; label estimates and never invent savings. If recurring inefficiency needs retrospective analysis, use the existing audit skill rather than duplicating it here.

## Token checkpoints during work

At existing stage transitions, before an expensive next step, or after repeated retries/large outputs, check usage from evidence already available. Skip extra telemetry calls, continuous polling, and separate reports for routine tasks.

- **Measured:** use task-scoped token counters only when exposed. State the source, scope, and counting method; distinguish input/output/cache figures and avoid adding overlapping cumulative totals. Account-wide limits, context capacity, and tool-wrapper savings are not task token consumption.
- **Proxy:** when task totals are unavailable, use observed repeated reads, retries, output size, and progress as warning signals. Label tool-output token estimates as partial estimates, never total or billed usage. If there is no evidence, say usage is unavailable when asked; do not fabricate a number or claim the task is cheap.
- **Budget:** reuse a user-specified budget and its scope. With a compatible measured counter, warn once at 80% (or the user's chosen threshold), then again only on a meaningful change. Respect a hard limit; report unfinished required verification rather than skipping it and claiming completion. Without a budget or comparable baseline, do not invent a universal definition of "too many tokens".
- **Action:** if usage approaches the budget or avoidable repetition is evident, briefly report the evidence, likely cause, and cheaper next step. Reduce waste within approved scope immediately. Token alerts alone do not trigger two confirmations; request a decision only when the existing risk/scope rules require one. Stay quiet when there is no actionable change.
